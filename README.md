# Session 09 · Agent Lab

사용자의 목표에 따라 에이전트가 도구를 고르고, 서버 코드가 직접 실행하고, 결과를 다시 모델에 전달하는 단일 플로우

```text
입력: AI 반려동물 앱 아이디어를 검증해줘
search_ideas → get_market_info → save_report → 최종 요약
```

## 내 에이전트의 목표와 범위

목표: 사용자가 기획하고 싶은 행사의 목적·대상·지역·예산을 입력하면, 유사 행사 레퍼런스 3~5개를 조사하고 출처와 함께 비교하여 적용할 아이디어, 차별화 방향, 운영 시 주의점을 제안한다.

하지 않을 것:
- 사용자 승인 없이 결제, 예약, 광고 집행이나 외부 업체 연락을 하지 않는다.
- 미공개 기획안과 참가자 개인정보를 외부로 전송하지 않는다.
- 기존 기획안과 리포트를 임의로 삭제하거나 덮어쓰지 않는다.
- 확인되지 않은 행사 정보나 출처를 만들어내지 않는다.

## 스텝 2. 도구 설계 검토 프롬프트

아래는 행사 에이전트의 도구 설계 초안을 검토하기 위한 프롬프트입니다. 현재 구현은 기존 앱 아이디어 데모이며, 아래 도구는 아직 구현하지 않았습니다. 검토 후 최종 설계는 참가자가 결정합니다.

```markdown
내가 만들려는 에이전트는 행사 아이디어를 입력받아 유사 행사 레퍼런스를 조사하고 기획 조언을 제공하는 에이전트야.

첫 실습에서는 직접 준비한 행사 레퍼런스 DB를 사용해. 실제 웹 검색은 하지 않으며, DB 자료를 실시간 웹 조사 결과라고 표현하면 안 돼.

내 에이전트의 도구 설계 초안이야:

| 이름 | 입력 | 출력 | description |
|---|---|---|---|
| search_events | keyword: string, region?: string, limit?: number (기본 5, 최대 10) | 행사 목록: id, 행사명, 짧은 소개, 지역, 출처 URL | 유사 행사 후보를 찾거나 검색 결과가 부족해 검색어·지역을 바꿔 재검색할 때 사용한다. 행사 DB에서 조건에 맞는 후보 목록을 조회한다. 읽기 전용. |
| get_event_details | event_ids: string[] | 행사별 목적, 대상, 형식, 규모, 참가비, 운영 특징, 출처 URL, 확인되지 않은 항목 | 검색한 후보 중 비교할 행사의 상세 정보가 필요할 때 사용한다. 검색 결과의 ID로 DB의 상세 자료를 조회한다. 자료에 없는 값은 ‘확인되지 않음’으로 반환한다. 읽기 전용. |
| save_report | title: string, summary: string, references: array, suggestions: string[], risks: string[] | report_id, 저장 성공 여부 | 조사와 조언을 정리한 뒤 사용자가 저장을 요청하거나 동의했을 때 사용한다. 출처를 포함한 리포트를 새로 저장한다. 기존 자료를 수정하거나 삭제하지 않는 쓰기 작업. |

행사 비교와 기획 조언 작성은 LLM이 조회 결과를 바탕으로 수행하고, 별도 도구로 만들지 않을 거야.

지켜야 할 범위:
- 사용자 승인 없이 결제, 예약, 광고 집행이나 외부 업체 연락을 하지 않는다.
- 미공개 기획안과 참가자 개인정보를 외부로 전송하지 않는다.
- 기존 기획안과 리포트를 임의로 삭제하거나 덮어쓰지 않는다.
- 확인되지 않은 행사 정보나 출처를 만들어내지 않는다.

코드는 쓰지 말고 아래만 검토해줘.
1. description이 모호해서 LLM이 엉뚱한 도구를 고를 수 있는 곳
2. 도구끼리 역할이 겹치는 곳
3. 입력/출력에서 빠진 필드, 자료형, 제한 조건, 결과 없음·오류 처리
4. 쓰기 도구의 사용자 확인이 필요한 시점과 중복 저장 방지 방법

고칠 점은 ‘도구 이름 / 문제점 / 수정 제안 / 이유’ 표로 제안만 해줘.
파일 수정이나 구현은 하지 말고, 최종 결정은 내가 할게.
```

## 빠른 시작

필요 환경: Node.js 20.9 이상, OpenAI API 키, Supabase 프로젝트.

1. `.env.example`을 `.env.local`로 복사하고 OpenAI 키·모델, Supabase URL·publishable key를 입력합니다.
2. Supabase SQL Editor에서 `supabase/schema.sql`을 실행한 뒤 `supabase/seed.sql`을 실행합니다.
3. `npm install` 후 `npm run check:env`, `npm run dev`를 실행합니다.
4. 화면의 샘플 요청을 실행하고 우측 로그와 Supabase의 `agent_reports` 테이블을 확인합니다.

환경 점검 스크립트는 환경변수 확인 후 OpenAI 최소 호출과 Supabase의 기존 `ideas` 테이블 읽기를 수행합니다. OpenAI 호출에는 소액 비용이 발생할 수 있습니다. 비밀값과 행 내용은 출력하지 않으며 DB 쓰기는 하지 않습니다. 세 검사 모두 OK여야 연결 확인이 완료됩니다. Supabase publishable key는 브라우저에 노출 가능한 키이며, 두 자료 테이블은 RLS 읽기 정책, 리포트 테이블은 삽입 정책으로 제한합니다. 서비스 롤 키는 사용하지 않습니다.

## 스텝 3. 개발 문서와 연결 검사

- [PRD.md](PRD.md): 행사 에이전트의 목표, 도구 목록, 성공 기준과 범위.
- [CLAUDE.md](CLAUDE.md): 최대 단계 수, 도구 분리, 쓰기 전 사람 확인, 출처와 개발 규칙.
- `npm run check:env`: 환경변수, OpenAI 호출, Supabase 조회 확인.

행사 도구와 저장 확인은 아직 설계 단계입니다. 현재 앱의 실행 루프는 기존 데모를 유지합니다. 두 문서의 Git 커밋과 연결 검사 통과 여부는 각각 확인해야 합니다.

## 레포 구조

```text
src/
  agent/runAgent.ts       # Responses API 도구 호출 루프와 max_steps
  tools/                  # 검색, 시장 자료 조회, 리포트 저장
  config/demo.ts          # 모델과 에이전트 지침
  lib/                    # Supabase 클라이언트와 공유 타입
  app/api/agent/route.ts  # 입력 검증과 API 오류 처리
  components/AgentDemo.tsx # 목표 입력, 단계별 실행 로그, 결과
scripts/check-env.mjs     # 환경변수 사전 점검
supabase/schema.sql       # RLS가 적용된 실습 테이블
supabase/seed.sql         # 데모 아이디어·시장 참고자료
AGENTS.md                 # 에이전트 도구 공통 실습 규칙
```

`search_ideas`와 `get_market_info`가 읽는 자료는 흐름을 재현하기 위한 가상 시드 데이터입니다. 실제 시장 조사 결과로 인용하지 않습니다. 실습 용도라 익명 리포트 저장을 허용하므로 공개 서비스로 배포하기 전에는 로그인, 사용자별 권한, 쓰기 제한을 추가해야 합니다.

## 실습 확장

새 기능은 `src/tools/`에 서버 함수와 JSON Schema를 추가하고, `src/agent/runAgent.ts`의 실행 맵에 등록합니다. 기존 루프의 대화 기록과 `call_id` 연결은 그대로 유지합니다. 실행 횟수는 `src/lib/shared.ts`의 `MAX_STEPS`에서 조절합니다.
